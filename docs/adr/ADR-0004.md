# ADR-0004: Freshness model — end-to-end command expiry with bounded uncertainty

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Autonomous Taxi team
- **Supersedes:** None

> **Implementation status:** this ADR records an architectural **decision**, not shipped code.
> The tiers, modules and firmware files it names are **specifications that have not been
> implemented** in this repository. The v0.1 simulation, the ESP32-CAM starter and the Arduino
> bench parser are what exist today. See [docs/VALIDATION.md](../VALIDATION.md) for the verified
> state of the current tree.


## Context

`docs/PROTOCOL.md` states the freshness requirement for the future movement protocol,
and it is the requirement that most directly determines whether the vehicle is safe:

> "2. End-to-end freshness. A TTL measured only from Arduino receive time is
> insufficient: an old queued command must never acquire a new lifetime on late
> arrival. Use a tested challenge/response or synchronized-clock age scheme with
> bounded uncertainty."

and

> "3. Arduino-owned command watchdog, local obstacle stop and hardware disable
> interface. Invalid frames and generic heartbeats must not renew movement authority."

### The defect in the original draft's "heartbeat renews authority" model

The original design proposal used a heartbeat model: the host sends periodic heartbeats,
and the receipt of a heartbeat extended the vehicle's authority to keep executing the
last commanded motion. The problem with that model is that it treats a liveness signal
as an authorisation signal, and the two are not the same thing.

The specific failure is a **stale command acquiring a new lifetime on late arrival**.
Consider the sequence:

1. At `t = 0` the host emits a motion command, `M1`, and it is queued somewhere in the
   path (a congested Wi-Fi link, a backed-up relay queue, a stalled host socket).
2. The command sits in the queue for a second.
3. Meanwhile the host continues to send heartbeats, which arrive promptly and keep the
   authority alive.
4. At `t = 1000 ms` the queue drains and `M1` finally arrives at the Arduino.
5. The Arduino sees a recently-arrived command. It is recent *at the receive time*.

Step 5 is the failure. The vehicle executes a one-second-old command. If the host had
changed its mind at `t = 100 ms` — because an obstacle appeared, or because the mission
was cancelled — the vehicle will nonetheless execute the command it had already
superseded. The heartbeat made the stale command look new.

The same failure occurs without any heartbeats at all, in a simpler and more damaging
form: the host stops sending commands entirely because it has crashed or hung. The
Arduino receives nothing. The command it holds is the last one it received, and if the
Arduino's rule is "keep executing the last command until a newer one arrives", the
vehicle drives into whatever caused the host to stop. This is why the arbiter's
watchdog tier exists at all — but a watchdog alone does not fix the late-arrival case,
because a watchdog measures time since the last *arrival*, and a late arrival resets it.

The correct property is **end-to-end**: a command's authority is a function of how long
ago the command was *produced*, not how long ago it was *received*. Every hop that
delays a command delays its expiry, and that delay must be visible to the receiver.

### What the implementation is to provide

`taxi/protocol/motion.py` is to implement the model this ADR records. The shapes below are the
specified API.

**The command.** `MotionCommand` is a frozen dataclass carrying `version`,
`session_id`, `sequence`, `linear`, `angular` and `timestamp_ms`. `PROTOCOL_VERSION` is
`1`.

**The default age limit.** `DEFAULT_MAX_AGE_S = 0.3` — 300 ms.

**The freshness predicate.** `is_fresh(command, now_ms, max_age_s=DEFAULT_MAX_AGE_S,
clock_uncertainty_ms=0)` computes:

```python
age_ms = now_ms - command.timestamp_ms
tolerance = int(max_age_s * 1000) + max(0, clock_uncertainty_ms)
if age_ms < -clock_uncertainty_ms:
    return False
return age_ms <= tolerance
```

Three properties of this predicate matter, and each has a test in
`tests/test_protocol_freshness.py`:

- **A late-arriving command does not gain a new lifetime.** The test
  `test_a_late_arriving_command_does_not_gain_a_new_lifetime` creates a command at
  `t = 0` and evaluates it at `t = 1000`. It is rejected. Age is computed from the
  command's own timestamp, never from arrival time.
- **A future-dated command is rejected.** The test
  `test_a_command_from_the_future_is_rejected` creates a command timestamped at
  `t = 5000` and evaluates it at `t = 1000`. It is rejected, because a future timestamp
  cannot be trusted to age out correctly — the command would live longer than its
  nominal window if the clock were later corrected.
- **Clock uncertainty widens the window rather than loosening the check.** The test
  `test_clock_uncertainty_widens_the_window` shows that a command which is 350 ms old
  against a 300 ms limit is rejected with zero uncertainty and accepted with 100 ms of
  declared uncertainty. Uncertainty is declared explicitly, not absorbed silently.

**Where the check lives.** The `taxi/protocol/motion.py` module docstring is to state the
placement rule:

> "Freshness is enforced here rather than in the transport layer so that every path
> into the Arduino applies the same rule: a command that is too old, or that arrives out
> of order, is rejected. It is never applied retroactively."

**The session and sequence are carried end to end.** `MotionCommand.create` masks
`session_id`, `sequence` and `timestamp_ms` to 32 bits. `UartMotionPacket` in
`taxi/protocol/transport.py` is to carry all six fields, and its docstring is to state the
intent:

> "The timestamp is carried even though the Arduino also has its own clock: the
> Arduino uses it to reject commands that were queued before a session change, and the
> sequence number to reject reordered frames."

### The Arduino side

`firmware/arduino/src/watchdog.h` is to state the rule that closes the loop:

> "The watchdog is the reason a stalled laptop or a dropped Wi-Fi link cannot leave the
> vehicle moving. It is deliberately independent of the host: only a fresh, valid,
> in-session command renews it, and nothing else does."

and `Watchdog::Reset()` leaves the watchdog "in the expired state, so a fresh boot
cannot move."

The ESP32-S3 relay task in `firmware/esp32_s3/src/main.cpp` is to hold `lastSession`,
`haveSession` and `lastSequence` state and states its role: "The gateway does not
decide whether a command is safe; that is the Arduino's job. It does check the frame
integrity and the session/sequence ordering so that a stale or reordered frame never
reaches the UART."

## Decision

We adopt an end-to-end freshness model with **monotonic sequence**, **session
identifier**, and an **explicitly bounded clock uncertainty**. The model has four
rules.

### Rule 1 — Age is measured end to end, from the command's own timestamp

A motion command carries the millisecond timestamp at which it was produced. The
receiver computes the age from that timestamp against its own clock and rejects the
command if the age exceeds the limit.

A command that arrives after its window has closed is **rejected on arrival**. It does
not receive a fresh lifetime. The receiver never uses arrival time as a proxy for
command age.

The default limit is `DEFAULT_MAX_AGE_S = 0.3` seconds.

### Rule 2 — Both expired and future-dated commands are rejected

The acceptance window is closed at the front as well as the back:

```text
        age_ms = now_ms - timestamp_ms
  reject if  age_ms < -clock_uncertainty_ms        (future-dated)
  reject if  age_ms > max_age_ms + clock_uncertainty_ms   (expired)
  accept otherwise
```

A future-dated command is rejected as firmly as an expired one. The reasoning is that a
timestamp in the future cannot be trusted to age out correctly: if the clock is later
corrected, or if the sender's clock drifts backwards, the command's actual lifetime
would exceed the nominal limit. Accepting it would mean the receiver has granted a
command more time than it claims to have checked.

### Rule 3 — Clock uncertainty widens the window; it never loosens the freshness rule

`clock_uncertainty_ms` is an explicit, declared bound on how far the sender's and
receiver's clocks may disagree. It is added to the permitted age and is subtracted from
the permitted future offset, so it makes the check *symmetric and explicit* rather than
lenient.

The important property is that uncertainty **cannot extend a command's life beyond the
age limit in an undeclared way**. If the sender and receiver clocks are known to be
within ±50 ms, that is declared as `clock_uncertainty_ms = 50`, and the effective
window is exactly 50 ms wider than the nominal. The uncertainty is a number in the
code, not an implicit tolerance.

### Rule 4 — A heartbeat or ping never renews movement authority

`PING_PACKET_TYPE = 0x02` exists in the protocol, and `MOTION_PACKET_TYPE = 0x01` and
`TELEMETRY_PACKET_TYPE = 0x03` are distinct. A ping is a liveness probe. It does not
carry a velocity, and it does not renew the watchdog.

Only an **accepted** motion command renews the watchdog, where "accepted" means it
passed, in order:

1. the frame integrity check (CRC-8, per ADR-0003);
2. the session check — the command's `session_id` must match the current session;
3. the ordering check — the command's `sequence` must be strictly greater than the last
   accepted sequence;
4. the freshness check of Rules 1 to 3.

This is a direct implementation of the `docs/PROTOCOL.md` requirement that "Invalid
frames and generic heartbeats must not renew movement authority", and of the
`AGENTS.md` rule that "Reconnect never authorizes motion".

### Rule 5 — Session change flushes pending commands

`session_id` changes whenever motion authority is (re)established. The `MotionCommand`
docstring states the contract:

> "`session_id` changes whenever motion authority is (re)established. The Arduino
> discards frames from a previous session, so a command queued before a reconnect
> cannot be applied after it."

On a session change:

- the last-accepted sequence is reset, so ordering restarts within the new session;
- any command from the previous session is discarded, whether it is in flight on the
  network hop, queued in the relay, or already buffered on the Arduino;
- the watchdog is reset to the expired state, so motion is not granted until the first
  accepted, fresh command of the new session arrives.

This is the mechanism that makes "reconnect never authorises motion" true at the wire
level rather than only at the API level.

### Rule 6 — Sequence replay and reordering are rejected

The sequence number is monotonic within a session. A command whose sequence is not
strictly greater than the last accepted sequence is rejected. This rejects:

- **replays** — an attacker or a stale queue re-sending a previously accepted command;
- **reordering** — an older command arriving after a newer one has been accepted;
- **duplicate delivery**, which a UDP path or a retransmitting transport can produce.

Note that the sequence check and the timestamp check are independent and both are
required. The sequence number alone does not establish age, because it carries no time
information; the timestamp alone does not establish ordering, because two commands
created in the same millisecond would have equal timestamps.

## Consequences

### Positive

- A command that arrives late is rejected rather than obeyed. The specific failure the
  original draft's heartbeat model permitted — a queued command gaining a new lifetime
  — is closed.
- A stalled or crashed host resolves to stop, because the watchdog is renewed only by
  a genuine command and a ping cannot renew it.
- The clock-uncertainty bound is explicit and auditable. A reader can see exactly how
  much slack the system allows and can go and measure it.
- Future-dated commands are rejected, closing a hole that would otherwise let a
  misconfigured or malicious sender extend a command's life.
- The session identifier makes reconnect semantics unambiguous and testable, and it
  gives the Arduino a way to discard everything queued before a reconnect.
- The freshness rule lives in `taxi/protocol/motion.py`, not in the transport, so every
  path into the Arduino applies the same rule. There is no transport-specific bypass.
- The host-side and firmware-side checks are independent. The ESP32 relay filters
  session and sequence ordering before a frame reaches the UART, and the Arduino
  applies the full check itself. Either one alone would be sufficient for safety;
  both together mean a relay bug does not become a motion-authority bug.

### Negative / costs

- Every command carries 8 bytes of session and sequence overhead plus 4 bytes of
  timestamp. The motion packet is 18 bytes because of this, not 8.
- A synchronised-clock scheme requires the sender's and receiver's clocks to be
  related. The bound `clock_uncertainty_ms` must be *measured* on the real system; it is
  currently a parameter with a default of `0`, which is optimistic.
- Monotonic sequence numbers must wrap. At 32 bits and any realistic command rate the
  wrap is unreachable in a session's lifetime, but the comparison must be written to
  handle it correctly (a signed difference comparison, not a naive `>`).
- The freshness check is applied at more than one hop, so a command must satisfy the
  constraint twice with slightly different clocks. This is cheap but it does mean the
  effective end-to-end window is the intersection of the hops' windows, not the
  loosest one.
- The `NetworkCommand` frame does not currently carry a timestamp (ADR-0003 records
  this), so the network hop's age is established by session and sequence ordering
  rather than by a timestamp. **Not implemented — target design**: the Arduino's binary
  frame decoder and the full accept path, which would evaluate the timestamp against
  the Arduino's own clock.

### Risks accepted

- **The Arduino has no synchronised clock yet.** The Arduino counts `millis()` from
  boot. Its clock and the host's clock are unrelated. Until a synchronisation scheme
  is implemented, the timestamp comparison across the UART hop cannot be performed
  correctly by the Arduino alone, and `clock_uncertainty_ms` would have to be set to
  cover the entire offset between two free-running clocks, which is unbounded in
  principle. This is the single largest open item in the freshness model.
- The 300 ms default age limit is a placeholder aligned with the provisional watchdog
  timeout. Both must be re-derived from measured end-to-end latency; see ADR-0006. If
  the measured worst-case latency exceeds the age limit, every command will be
  rejected and the vehicle will not move at all — a fail-safe failure mode, but one
  that would be obvious on the bench.
- The session identifier must be unpredictable enough that a stale frame cannot
  accidentally match the current session. The `MotionCommand` masks it to 32 bits.
- Two independent clock domains means the age check and the watchdog are not measuring
  the same thing. The watchdog measures time since the last accepted arrival; the
  freshness check measures the age of the command as produced. Both must expire for
  the vehicle to be safe, and the effective stop time is the later of the two.

## Alternatives considered

**Heartbeat-renewed authority (the original draft's model).** Rejected. It conflates
liveness with authorisation and permits a stale queued command to acquire a new
lifetime on late arrival. It also means a heartbeat storm can keep a vehicle moving
after the host has stopped issuing motion commands.

**TTL measured only at the Arduino receive time.** Rejected explicitly by
`docs/PROTOCOL.md` for the reason above. A receive-time TTL is a transport-liveness
timer, not an age check.

**No freshness check at all, relying on the watchdog alone.** Rejected. The watchdog
measures arrival spacing, not command age. A command that arrives once and then a
steady heartbeat stream arrives would keep the watchdog alive indefinitely under a
heartbeat model, and under a no-heartbeat model a single late arrival would reset the
watchdog. Neither bounds the age of the executed command.

**Challenge/response (the other option named in `docs/PROTOCOL.md`).** Not rejected on
principle; deferred. A challenge/response proves that the Arduino heard a *recent*
challenge, but it still does not age the *command* that was queued behind it, unless
the command is bound to the challenge round. It is more machinery than the command
path needs and it costs a round trip in the latency budget. It remains the right
fallback if the clock-uncertainty bound proves unsatisfiable.

**Trusting the relay to enforce freshness and letting the Arduino trust the relay.**
Rejected. It moves the authority boundary upward, which is exactly what ADR-0001
forbids. The Arduino applies the check itself.

**Using a host-assigned absolute timestamp with no receiver clock comparison, and
letting the receiver reject only "clearly old" commands.** Rejected. This is the
"assume the clocks are close" version of the scheme, and it silently fails when the
clocks are not close. An explicit bound, even if large, is preferable to an implicit
assumption.

**Rejecting only future-dated commands and accepting everything not-yet-expired.**
Rejected, and this is a correction to the draft's thinking. Accepting a future-dated
command means the receiver has granted time it has not accounted for. The symmetric
window — bounded at both ends — is the only formulation that makes the age claim true.

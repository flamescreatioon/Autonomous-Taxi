# ADR-0002: ESP32-S3 as primary edge target; ESP32-CAM demoted to a working bench fallback

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Autonomous Taxi team
- **Supersedes:** None

> **Implementation status:** this ADR records an architectural **decision**, not shipped code.
> The tiers, modules and firmware files it names are **specifications that have not been
> implemented** in this repository. The v0.1 simulation, the ESP32-CAM starter and the Arduino
> bench parser are what exist today. See [docs/VALIDATION.md](../VALIDATION.md) for the verified
> state of the current tree.


## Context

`AGENTS.md` states the original goal in terms of an ESP32-CAM: "Build a campus taxi using
Python on a laptop, ESP32-CAM for camera / communication and Arduino for local sensor /
motor control." The v0.1 repository reflects that: `firmware/esp32_cam/` is the edge
target, with an AI Thinker ESP32-CAM / OV2640 board, a `src/main.cpp` carrying the
embedded AI Thinker camera pin map, and a `src/config.example.h` for the Wi-Fi
credentials and device token.

That board works, and it keeps working. The v0.1 firmware exposes authenticated
`/capture`, `/telemetry` and `/stop` over local HTTP, and `scripts/camera_probe.py`
fetches a single JPEG against it. The decision recorded here does not withdraw that
support. It changes which board is the *primary* target for the three-tier architecture
of ADR-0001, and why.

### Why the ESP32-CAM is insufficient as the primary edge tier

The requirements for Tier 2, derived from the target architecture, are:

1. A camera path that can sustain a frame rate with bounded latency, without allocating
   on the heap in steady state.
2. A WebSocket client that stays connected to the laptop without blocking the camera
   path.
3. A UART bridge to the Arduino that runs concurrently with both of the above.
4. Enough memory for dual frame buffers in PSRAM.

The AI Thinker ESP32-CAM has a single-core ESP32 with roughly 4 MB of external PSRAM
and no PSRAM on the module itself in the usual configuration. Its camera driver is the
older `esp_camera` API with a fixed, compile-time pin map baked into the board
definition. That pin map is the board's, not the chip's, and it constrains the camera
to a specific module layout.

The decisive issue is not the camera sensor but the **system-on-chip**. The ESP32-CAM's
ESP32 has one Xtensa core. The Tier 2 design requires the camera DMA and the network
stack to make progress independently of the UART relay and of each other, because a
capture deadline missed is a dropped frame and a telemetry sample that is one cycle late
is merely stale. On a single core with a single FreeRTOS priority ordering, every one of
those deadlines is a deadline against every other. The camera task would have to outrank
the network task to avoid dropping frames, which in turn means a stalled WebSocket
handshake can starve the telemetry path and therefore starve the Arduino's view of the
vehicle.

### Why the ESP32-S3 fits

The ESP32-S3 provides two Xtensa LX7 cores, so I/O work and protocol work can be
pinned to different cores and proceed in parallel. It also provides substantially more
PSRAM and a more capable camera interface, including PSRAM-resident dual frame buffers.

`firmware/esp32_s3/src/main.cpp` is to encode the resulting task layout:

```c
constexpr UBaseType_t kCameraTaskPriority   = 5;
constexpr UBaseType_t kNetworkTaskPriority  = 4;
constexpr UBaseType_t kRelayTaskPriority    = 3;
constexpr UBaseType_t kTelemetryTaskPriority = 2;
```

and the core affinity:

| Core | Task | Priority | Responsibility |
|---|---|---|---|
| 0 | `Task_NetworkClient` | 4 | WebSocket session, frame uplink, command downlink |
| 0 | `Task_CommandRelay` | 3 | Decode received commands, freshness-check, relay over UART |
| 1 | `Task_CameraCapture` | 5 | Camera DMA into PSRAM, JPEG encode, frame handoff |
| 1 | `Task_TelemetryPoll` | 2 | Poll the Arduino for telemetry, publish upstream |

The priorities are deliberate. The camera task sits highest because a missed capture
deadline is a dropped frame, and frames are the most latency-sensitive thing the gateway
carries. The telemetry poll sits lowest because a telemetry sample one cycle late is
merely stale, and stale telemetry is explicitly invalid data rather than a safety
hazard. The two tasks that must not be starved by each other — camera and telemetry — are
on the same core and are separated by three priority levels; the two that must not
starve the camera — network and relay — are on the other core and are likewise separated.

The camera configuration target is **PSRAM dual frame buffers** (`fb_count=2`),
`PIXFORMAT_JPEG`, QVGA or VGA, `jpeg_quality=12`. Two buffers let capture continue while
the previous frame is encoded and transmitted, without heap allocation in steady state.
`firmware/esp32_s3/platformio.ini` is to build for `esp32-s3-devkitc-1` on
`platform = espressif32@6.9.0` with `-DBOARD_HAS_PSRAM` and
`-DARDUINO_USB_CDC_ON_BOOT=1`.

The UART bridge runs at 115200 baud with the COBS/CRC-8 framing of ADR-0003.

### The constraint that the decision does not relax

Whichever board is chosen, **no pin is guessed.** `firmware/esp32_s3/src/main.cpp`
leaves every camera pin and both UART pins at `-1`:

```c
constexpr int kUartTxPin = -1;
constexpr int kUartRxPin = -1;
constexpr int kCameraPinD0 = -1;
...
```

With both UART pins unset, `setup()` is to print "UART pins unconfirmed; bridge disabled" and
`gUartEnabled` is to stay false, so no frame can reach the Arduino. A guardrail test
(`tests/test_safety_invariants.py`, to be written) is to fail the build if any `kCameraPin*`,
`kUartTxPin` or `kUartRxPin` constant is given a value. The camera pin map in the ESP32-S3 source
is to be commented as "the common ESP32-S3 devkit layout" that "MUST be confirmed against the
actual module before it is used".

This is the same discipline `docs/HARDWARE.md` applies to the ESP32-CAM: "The AI Thinker
camera pin map is embedded in main.cpp and must match the actual module."

## Decision

**The ESP32-S3 is the primary edge target for Tier 2.** `firmware/esp32_s3/` is the
directory that the v2 architecture, the framing mirror, the protocol constants and the
future release notes point at.

**The ESP32-CAM is retained as a working bench fallback**, not deleted and not
deprioritised to a broken state. `firmware/esp32_cam/` remains:

- a supported target with its own `platformio.ini` and its own `src/main.cpp`;
- the currently usable way to take a JPEG from a camera on the bench via
  `scripts/camera_probe.py`;
- the fallback for any bench work where the ESP32-S3 board is not the confirmed module
  or where a confirmed ESP32-S3 is not available.

`firmware/esp32_cam/` keeps its embedded AI Thinker camera pin map and its
`src/config.example.h` credentials template, because that map is correct *for that
module* and the module is a supported bench part.

The two targets are kept deliberately asymmetric in scope, and this asymmetry is
recorded rather than hidden:

| | ESP32-S3 (primary) | ESP32-CAM (fallback) |
|---|---|---|
| Role in v2 | Tier 2 edge gateway | Bench-only camera / telemetry capture |
| Present in this repository | **No** — target not yet implemented | **Yes** — working starter, compiles |
| FreeRTOS task layout | Specified (4 tasks, pinned to 2 cores) | Not applicable |
| COBS/CRC-8 framing | Specified (`firmware/esp32_s3/src/framing.{h,cpp}`) | No — v0.1 newline-ASCII UART only |
| Binary motion downlink | Protocol constants specified (`protocol.h`) | Not implemented |
| Camera | Not yet written; pins to be unset | Working single-JPEG HTTP capture |
| UART to Arduino | Bridge present but disabled (pins unset) | `/stop` relay only, unvalidated line |

**The demotion is a scope statement, not a quality judgement.** The ESP32-CAM firmware
is the more complete of the two *today* — it actually opens a camera and serves HTTP,
while the ESP32-S3 camera and network tasks are stubs. The decision is about which board
will carry the v2 architecture, and it is made on hardware capability, not on current
firmware completeness.

**The S3 is the only board on which the UART bridge will be enabled**, because ADR-0003
and ADR-0004 put the freshness and framing enforcement on the ESP32 side of the UART
link. A board that cannot speak the framed protocol cannot be the primary edge tier.

## Consequences

### Positive

- The Tier 2 architecture gets the hardware it was designed around: two cores for
  independent I/O and protocol work, and PSRAM for dual frame buffers with no steady
  state heap allocation.
- The camera and network paths can make progress concurrently, which is a precondition
  for the latency budget in ADR-0006 to be achievable at all.
- The v0.1 camera work is not wasted. The ESP32-CAM stays usable for bench capture,
  which is exactly what M3 in `docs/ROADMAP.md` needs while the ESP32-S3 board is being
  confirmed.
- The framing implementation in `firmware/esp32_s3/src/framing.{h,cpp}` is to be a byte-for-byte
  mirror of `taxi/protocol/framing.py`, enforced by a shared-vector test. The primary target is therefore the one whose
  wire format is already under cross-language test.
- The S3's USB CDC support means the debug and serial console no longer competes with
  pins 0/1, which `docs/HARDWARE.md` flags as a real constraint on the Uno ("USB serial
  is shared with pins 0/1 on an Uno; avoid programmer/relay contention").

### Negative / costs

- Two edge targets to maintain, with different pin maps, different camera APIs (the S3
  target uses the newer camera API; the ESP32-CAM target is pinned to the Arduino-ESP32
  2.x camera API), and different network stacks. The v0.1 ESP32-CAM cannot be upgraded
  to the v2 binary protocol without a rewrite of its UART handling.
- The ESP32-S3 firmware currently does less than the ESP32-CAM firmware. Its camera and
  network task bodies are stubs that idle on `vTaskDelay`. Two things follow: the
  target has more work to reach parity, and any claim that the S3 "works" today would be
  false.
- The S3 devkit's pin map is not the AI Thinker map. Confirming the actual module
  before enabling any pin is unavoidable work, and it is gated on hardware facts the
  team does not yet have.
- `docs/HARDWARE.md` must be updated to record the ESP32-S3 as the primary edge board.
  Until then, the table of "must confirm" items in that document is incomplete for the
  primary target.

### Risks accepted

- **The primary target is less functional today than the fallback.** Accepted. The
  fallback covers the immediate need (a camera on the bench), and the primary target's
  shortcoming is stub code rather than a design flaw.
- **Neither firmware target has been compiled successfully in the development
  environment.** `docs/VALIDATION.md` records that "PlatformIO commands were attempted,
  but platform/toolchain downloads did not finish in this environment. Neither firmware
  target is claimed to compile successfully yet." The PlatformIO configuration for the
  S3 target is therefore written but unverified.
- The camera pin map in `firmware/esp32_s3/src/main.cpp` is described as a common devkit
  layout. If the confirmed module differs, the map must change — and the pin constants
  are currently guarded by a test that fails on any non-negative value, so that change
  is deliberately a deliberate act rather than a silent edit.
- The S3 camera driver API differs between Arduino-ESP32 major versions. The v0.1
  ESP32-CAM build notes in `docs/HARDWARE.md` warn: "The pinned Espressif platform uses
  the Arduino-ESP32 2.x camera API. If you upgrade the platform, check camera
  struct/API compatibility." The S3 target pins `espressif32@6.9.0` for the same reason.

## Alternatives considered

**ESP32-CAM as the primary edge tier.** Rejected on the single-core constraint and the
inability to run the camera path and the network path with independent deadlines. It
remains viable as a Tier 2 for a reduced feature set if the frame rate requirement is
relaxed, which is why it is retained rather than deleted.

**Raspberry Pi or similar Linux SBC as the edge tier.** Rejected for this project: it
would move Tier 2 into the same failure class as Tier 1 (a general-purpose OS running
an unbounded software stack), which defeats the purpose of the tier split. It would also
make the "laptop dies → gateway stops relaying → Arduino watchdog fires" chain depend on
an OS that might not schedule the relay task promptly. The ESP32-S3 gives a comparable
role with a deterministic, small, single-purpose runtime.

**ESP32 (original, single-core, no PSRAM) as a cheaper S3 substitute.** Rejected. It has
the same single-core scheduling constraint as the ESP32-CAM.

**Skip Tier 2 entirely and put the camera on the laptop via USB.** Rejected. The camera
would then be on the same host that is assumed to be able to fail, and the USB camera
bandwidth would compete with the WebSocket downlink on the same machine. It also
eliminates the natural enforcement point for the ADR-0004 downlink freshness checks.

**ESP32-S3 replacing the Arduino as the Tier 3 board.** Rejected. It would consolidate
actuation into the tier that also runs the camera and the network stack, reintroducing
exactly the coupling ADR-0001 exists to prevent. The Arduino's AVR simplicity and
determinism are an asset for a 20 ms hard real-time loop, not a limitation to be
engineered away.

# ADR-0001: Three-tier control model and downward-only safety authority

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Autonomous Taxi team
- **Supersedes:** None

> **Implementation status:** this ADR records an architectural **decision**, not shipped code.
> The tiers, modules and firmware files it names are **specifications that have not been
> implemented** in this repository. The v0.1 simulation, the ESP32-CAM starter and the Arduino
> bench parser are what exist today. See [docs/VALIDATION.md](../VALIDATION.md) for the verified
> state of the current tree.


## Context

The v0.1 system in this repository is a Python/FastAPI simulation with an ESP32-CAM bench
starter and an Arduino Uno bench parser. The board starters have never been able to move
anything: `firmware/arduino/src/main.cpp` has no actuator GPIO, the sonar echo callbacks
`onTrigger` and `onCapture` are empty, and the bench firmware rejects every motion request
with `motion_not_implemented`.

The next milestone is real motion, and the first architectural question is not "which
algorithm" but "where does the authority to move live". A single-board design that owned
perception, planning and actuation together would let the planner keep driving when its own
inputs degrade. The planner is the component most likely to fail in interesting ways: a
dropped frame, a stalled inference, a lost network, a hung process. If the same component
also owns the decision to energise a motor, then every one of those failures becomes a
reason to keep driving or an uncontrolled stop, and the safety behaviour is whatever the
Python process happened to do last.

The project has two hard rules that constrain the answer directly. From `AGENTS.md`:

- "Preserve terminal trip statuses and latched faults. Reconnect never authorizes motion."
- "Maintain separate application stop and physical emergency-stop concepts."

And from `docs/PROTOCOL.md`, for the future movement protocol:

> "Invalid frames and generic heartbeats must not renew movement authority."

The v0.1 host already encodes a version of this discipline. `taxi/mission/state.py` (to be
created) and
`taxi/supervisor.py` latch faults: clearing a fault input never resumes movement, an
explicit rearm is required, and a reconnect never authorises motion. That is a good
software property, but it is enforced by the *same* process that produces the commands.
If that process is the thing that has failed, the property is worth nothing to a vehicle
that is already moving.

The requirement therefore is not that the host be careful. It is that the host be unable to
grant authority to itself, and that the component which can actually energise a motor be
able to revoke it unilaterally without consulting anything upstream.

### The three tiers

The target architecture splits the system along the axis of "how much does this tier need
to be right, and what does it physically own".

**Tier 1 — Perception and planning (laptop, Python).** Camera frames in, `(v, ω)` out.
The pipeline is YOLO-family detection at the edge, lane perception, an occupancy grid,
VFH heading selection, and a motion controller that produces a normalised velocity vector.
The laptop is where the compute is and where the perception models live; it is also the
least reliable part of the system, because it is a general-purpose OS running an
unbounded set of third-party code.

**Tier 2 — Edge gateway (ESP32-S3, FreeRTOS).** Camera DMA into PSRAM, a WebSocket client
to the laptop, and a UART bridge to the Arduino. The gateway is a transport and sensor
aggregation tier. It has no actuators, no path planner and no collision policy. Its job
is to move bytes reliably and quickly, and to enforce the freshness rules of ADR-0004 on
the downlink.

**Tier 3 — Actuation and safety (Arduino Uno R3).** A 50 Hz (20 ms) cyclic non-blocking
loop, a three-phase round-robin sonar FSM, a subsumption arbiter, an Arduino-owned command
watchdog, and a differential kinematics solver. This tier owns the PWM outputs. It is
the only tier that can energise a motor.

### What the current code already encodes

The arbiter ordering is not a proposal; it is to be implemented in two places and asserted
equal. `firmware/arduino/src/arbiter.h` is to define:

```c
enum class Tier : uint8_t {
  kHardwareFailSafe = 0,
  kEmergencyReflex = 1,
  kNominalExecution = 2,
};
```

and `firmware/arduino/src/arbiter.cpp` is to evaluate them in that fixed order, failing out on
the first tier that applies. `taxi/mission/safety.py` is to mirror it with `TIER_ORDER` and
the docstring states that "The tier order is fixed and must match
`firmware/arduino/src/arbiter.h` and the documentation in `docs/adr/ADR-0001.md`". The
mirror is deliberately one-directional: the host-side arbiter "does not replace the
Arduino's decision: the hardware arbiter is authoritative, and a host decision can never
grant motion that the hardware has refused."

The watchdog is similarly Arduino-owned. `firmware/arduino/src/watchdog.h` is to state that
only "a fresh, valid, in-session command renews it, and nothing else does", and
`Watchdog::Reset()` leaves the watchdog "in the expired state, so a fresh boot cannot
move."

## Decision

We adopt a three-tier control model and the following rule as the central invariant of
the system.

> **Safety authority flows downward only.**
>
> Tier 1 may *request* motion. Only Tier 3 may *grant* it. Every tier below the requester
> is free to refuse, and refusal is the default.

### The three tiers and what each one owns

| Tier | Hardware | Owns | Never owns |
|---|---|---|---|
| **1. Perception & Planning** | Laptop (Python 3.10+, no ROS) | camera → detections → costmap → VFH → motion controller → `(v, ω)` | safety decisions, motor actuation |
| **2. Edge Gateway** | ESP32-S3 (FreeRTOS) | camera DMA, WebSocket client, telemetry forwarding, UART bridge | path planning, collision policy |
| **3. Actuation & Safety** | Arduino Uno R3 | sonar FSM, subsumption arbiter, watchdog, motor PWM | autonomy, route planning |

Tier 2 is never asked "is it safe to move?". It does not have the sensor timing, the loop
determinism or the physical outputs required to answer that honestly, and an untruthful
answer from a tier that cannot verify it would be worse than no answer. Tier 1 never
touches a motor; it produces a velocity *request* in a normalised range and nothing else.

### The subsumption arbiter ordering is fixed

The arbiter evaluates three tiers and selects the highest-priority one that applies:

| Priority | Tier | Condition | Effect |
|---|---|---|---|
| 0 | Hardware fail-safe | Watchdog expired (> 300 ms since the last accepted command) | Stop. Latched. |
| 1 | Emergency reflex | Centre distance < 20 cm, or side distance < 15 cm | Stop. |
| 2 | Nominal execution | Valid fresh command, sensors valid, drive armed | Execute `(v, ω)` |

Two properties of this ordering are load-bearing and are asserted by
a guardrail test (a guardrail test (`tests/test_safety_invariants.py`, to be written), to be written):

- **The watchdog outranks the reflex.** If the link has died *and* something is in front
  of the vehicle, the fail-safe tier is the one that speaks, because the reflex's distance
  data is itself only trustworthy while the board is alive.
- **A missing sensor does not trigger the reflex.** "No reading" is not "reading zero".
  The reflex fires only on a *valid* measurement below threshold. A missing sensor falls
  through to the fail-safe tier rather than being mistaken for an imminent collision.

The emergency thresholds (20 cm centre, 15 cm sides) and the watchdog timeout (300 ms)
are **provisional placeholders**, not physical limits. See ADR-0006.

### Loss of any tier resolves to stop

| Failure | Resolves to |
|---|---|
| Laptop process dies | Wi-Fi drops → ESP32 stops relaying → Arduino watchdog expires → stop |
| Laptop hangs (no commands) | Arduino watchdog expires at 300 ms → stop |
| Wi-Fi drops | Same as laptop death — the Arduino never sees a relayed command |
| Camera fails | Perception produces no detections → no fresh obstacle evidence → Tier 3 reflex governs |
| Sonar fails | Distance reads invalid → reflex cannot trigger, so Tier 3 refuses to grant nominal motion |
| Arduino reboots | Watchdog starts **expired**; motion is not granted until the first accepted, fresh command |

There is no "continue on last command" path anywhere in the design. The vehicle does not
have a cached trajectory it can coast through a link loss; it has a commanded velocity
that must be re-supplied within the watchdog window or it becomes zero.

### Reconnect never authorises motion

A reconnect restores *communication*, not *authority*. Specifically:

- The Arduino watchdog starts expired and is renewed only by an accepted, fresh,
  in-session motion command. A ping, a handshake, a reconnect or a liveness heartbeat
  does not renew it.
- Changing the session identifier flushes any pending commands; see ADR-0004.
- The `AGENTS.md` rule "Reconnect never authorizes motion" applies identically to the
  simulated supervisor and to the physical stack.

### The physical emergency stop is a fourth, independent path

The hardware emergency stop is not part of any of the three tiers. It is wired to
hardware, not to software, and no protocol, message, timeout or firmware update can
inhibit it. This keeps the "application stop" and "physical emergency stop" concepts
separate as required by `AGENTS.md`. The Arduino's fail-safe tier stopping the vehicle is
a *software* response to a *link* problem; it is not a substitute for a hardware disable
and must not be described as one.

## Consequences

### Positive

- Every failure mode of the most complex tier (the laptop) terminates in a bounded stop
  rather than in continued motion.
- The safety-critical code runs on the most deterministic platform available, in a
  20 ms loop with no blocking calls and no allocation.
- The Arduino remains genuinely independent of the host. A host bug cannot grant motion
  the hardware has refused, because the hardware's refusal is the last word.
- The tier split is testable. Each tier's contract can be tested in isolation with the
  tiers below it stubbed, and the arbiter ordering is asserted equal across the C++ and
  Python implementations.
- The design supports the v0.1 simulation remaining runnable. The simulator exercises the
  host-side mirror without any hardware present.

### Negative / costs

- Three hops, three clocks and three failure domains. The end-to-end latency budget in
  ADR-0006 is a consequence of this split, and it is tight.
- The Tier 2 gateway must be trusted to relay faithfully and promptly. It is trusted
  *not* to make safety decisions, which limits the damage a compromised or buggy gateway
  can do, but it can still delay or drop commands — and delay is handled by the watchdog.
- The host-side arbiter mirror in `taxi/mission/safety.py` is to be a second implementation of
  the same rules. It must be kept in step with `firmware/arduino/src/arbiter.h`, or the
  simulator will mislead the team about what the hardware does. The tier-order test
  exists for exactly this reason.
- Arduino's SRAM and CPU budget constrain the Tier 3 implementation: the sonar FSM, the
  arbiter, the watchdog and the kinematics solver must all fit alongside a byte-oriented
  frame decoder.
- The physical emergency stop is a separate wiring job with its own failure modes, and
  it must be tested independently of the software path.

### Risks accepted

- The 300 ms watchdog timeout is a placeholder carried from the design proposal. It is
  not derived from measured worst-case latency and may be either too tight (causing
  spurious stops under normal jitter) or too loose (allowing an unacceptable coast).
  ADR-0006 governs re-derivation.
- The 20 cm / 15 cm emergency thresholds are placeholders and are not derived from the
  measured stopping distance of the real vehicle with the real driver.
- The host-side arbiter being a mirror rather than the source of truth means a
  simulator run can pass while the hardware behaves differently, if the mirror drifts.
  The tier-order test mitigates but does not eliminate this.
- Tier 2's camera and network task bodies are stubs. The target FreeRTOS layout is
  implemented and the priorities are set, but no socket is bound and no camera is opened.
- Nothing in this ADR is hardware-tested. The v2 hardware tiers are scaffolded but
  inert; there is no code path from a Python call to a motor PWM write.

## Alternatives considered

**Single-board architecture (ESP32-S3 doing perception, planning and actuation).**
Rejected. It removes two hops and most of the latency budget, and it is the right answer
for a hobby robot. It is the wrong answer here because it puts the safety decision on the
same processor as the planner, with the same failure modes, and it removes the watchdog
boundary entirely: a hung FreeRTOS task that holds the mutex or the PWM registers cannot
be revoked by anything.

**Laptop-only with a dumb Arduino (or with no Arduino).** Rejected for the same reason in
reverse. The safety decision would live in a general-purpose OS process running
third-party model code, and the fail-safe would depend on the host's own liveness — the
property that is exactly what is missing when it matters.

**ESP32-CAM as the edge tier.** Rejected as the primary target; see ADR-0002. The
ESP32-CAM remains a supported bench fallback.

**Two tiers (laptop + Arduino, no gateway).** Rejected. The camera frame rate and the
UART bandwidth between a laptop and an Arduino would compete for the same link, and the
Arduino would have to carry the camera interface, which is well beyond its capability.
It also removes the natural place to do the downlink freshness checking that ADR-0004
requires.

**A safety-certified MCU (e.g. an automotive-grade part) in Tier 3.** Not rejected on
principle; deferred on cost and availability. The Uno R3 is adequate for a
campus-scale, low-speed, supervised vehicle provided the physical emergency stop is
independent. If the project graduates to a public road or passenger-carrying duty, the
Tier 3 part should be revisited.

**Allowing a host-side "continue on last command" mode for low-speed obstacle following.**
Rejected. It would make every link failure a motion failure rather than a stop, and it
would directly contradict the `AGENTS.md` rule that clearing a hazard never resumes
movement.

# ADR-0005: Speed and velocity domain and units — one canonical normalized scale

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Autonomous Taxi team
- **Supersedes:** None

> **Implementation status:** this ADR records an architectural **decision**, not shipped code.
> The tiers, modules and firmware files it names are **specifications that have not been
> implemented** in this repository. The v0.1 simulation, the ESP32-CAM starter and the Arduino
> bench parser are what exist today. See [docs/VALIDATION.md](../VALIDATION.md) for the verified
> state of the current tree.


## Context

The vehicle needs to express two motion quantities: a linear velocity `v` and an angular
velocity `ω`. Both are produced by the Tier 1 motion controller, carried over the
network hop, relayed over UART, and finally converted to wheel commands in Tier 3.

Every stage that touches these quantities must agree on two things: the **units** and
the **range**. Getting either wrong is not a cosmetic problem — it is a factor-of-ten
error in the commanded speed, or a silent saturation that turns a gentle turn into a
spin.

### The inconsistency in the original draft

The original design proposal specified **two different scales** on the two hops:

- The **network** packet carried `int16` linear and angular values over `±1000`.
- The **UART** packet carried `int8` linear and angular values over `±100`.

These are inconsistent in two separate ways, and the difference between them is not
merely a rounding detail.

**The range widths differ by a factor of ten.** `±1000` spans 2001 distinct values;
`±100` spans 201. The same physical command, sent over the network and relayed over
UART, has ten times the resolution on one hop as the other. A planner that produced a
command needing finer resolution than 201 steps would be quantised on the UART hop
alone — so the vehicle's actual behaviour would depend on which hop a given command
travelled, which is not something a system should have.

**The implicit full-scale values differ.** Even if the widths matched, an `int8` over
`±100` and an `int16` over `±1000` describe different physical quantities unless the
consumer of each knows the scale. A reader of the UART packet who assumed "int8, so
full scale is 127" and a reader who assumed "full scale is 100" would compute different
wheel commands from the same bytes.

**The draft did not say what the numbers meant.** No physical unit was attached to
`1000`. Was it millimetres per second? A PWM value? A normalised fraction times 1000?
The `docs/PROTOCOL.md` requirement is explicit: "Define physical units and ranges for
the actual drivetrain."

### The physical units are not yet known

`docs/HARDWARE.md` records that no motor driver is confirmed: the driver row reads
"None" under "Starter assumption" and "L298N, TB6612FNG or another driver" under "Must
confirm". The steering row reads "None" and "Differential motors or steering servo".
There are no encoders, no measured top speed, and no confirmed wheelbase.

So a **physical** speed domain — metres per second, or a fraction of a measured maximum
— cannot be defined yet, and any number chosen now would be a guess. `AGENTS.md` is
explicit: "Never enable physical outputs with guessed pins, driver types or safety
thresholds."

What *can* be defined now, unambiguously and without guessing, is a **normalised**
domain: a dimensionless fraction of the maximum commanded value, where "the maximum
commanded value" is defined by the vehicle's own calibration once it exists.

### What the implementation provides

`taxi/protocol/motion.py` is to define the canonical scale and the conversions:

```python
#: Canonical normalised scale. ``1000`` means "full scale".
MOTION_SCALE = 1000
```

`to_scaled` converts from the normalised domain to the wire:

```python
def to_scaled(value: float) -> int:
    clamped = max(-1.0, min(1.0, float(value)))
    return int(round(clamped * MOTION_SCALE))
```

`from_scaled` converts back:

```python
def from_scaled(value: int) -> float:
    return max(-1.0, min(1.0, value / MOTION_SCALE))
```

`MotionCommand` stores the scaled integers and exposes the normalised values through
the `linear_normalised` and `angular_normalised` properties.

The **clamping is deliberate**, and the docstring gives the reason: "Values outside
the range are clamped rather than wrapped, so a planner bug cannot produce an
unexpectedly large command." Wrapping would turn `1001` into `-999` — a sign flip. A
planner bug would then command a full-speed reversal instead of full-speed forward.
Clamping converts an unbounded planner error into a bounded, predictable one.

`tests/test_protocol_freshness.py` asserts the round trip
(`test_scaling_round_trips`) and the clamping behaviour
(`test_scaling_clamps_out_of_range_values`: `to_scaled(5.0) == MOTION_SCALE`,
`to_scaled(-5.0) == -MOTION_SCALE`).

### The explicit boundary conversion

`taxi/protocol/transport.py` is to provide the conversion to and from the 8-bit UART
domain, and names the defect it corrects:

```python
def normalise_for_uart(value: int) -> int:
    """Scale a wire-scale velocity down to the 8-bit UART domain.

    The original draft used ``int8 +/-100`` on the UART while using
    ``int16 +/-1000`` on the network. This keeps one canonical scale
    (:data:`~taxi.protocol.motion.MOTION_SCALE`) on the wire and converts
    explicitly at the boundary.
    """
    scaled = int(round(value * 127 / MOTION_SCALE))
    return max(-127, min(127, scaled))
```

with the inverse `expand_from_uart`. The conversion factor is `127 / 1000`, so
`+1000` maps to `+127` and `-1000` maps to `-127` — the full-scale endpoints survive
the conversion exactly.

### Tier 3's kinematics

`firmware/arduino/src/kinematics.h` is to solve the wheel commands from the normalised
vector:

```text
left  = clamp(linear - angular, -1, 1)
right = clamp(linear + angular, -1, 1)
```

`firmware/arduino/src/kinematics.cpp` is to implement exactly that, with `ClampUnit`
clamping to `[-1.0, 1.0]`. `firmware/arduino/src/arbiter.cpp` is to contain a second copy of
the same solver, `SolveWheelSpeeds`, with the comment:

> "The scale is a placeholder for the confirmed motor calibration and is not a
> physical speed limit."

The header is explicit that the PWM conversion is deliberately absent: "The scale from
a normalised command to PWM is deliberately absent: the PWM conversion needs the
confirmed motor driver and the measured calibration, which do not exist yet."

## Decision

**There is exactly one canonical velocity domain: a normalised dimensionless value in
`[-1.0, 1.0]`, where `1.0` means "full scale" and the full scale is defined by the
vehicle's calibration.**

### The canonical scale

`MOTION_SCALE = 1000` is the canonical on-wire scale. Every velocity that crosses a
hop boundary is carried as a signed integer in `[-1000, +1000]`, interpreted as
`value / 1000` in the normalised domain.

The scale is defined in exactly two places, and both must be changed together:

- `taxi/protocol/motion.py` — `MOTION_SCALE = 1000`
- `firmware/esp32_s3/src/protocol.h` — `constexpr int32_t kMotionScale = 1000;`

The firmware constant carries the comment "Canonical normalised velocity scale. See
ADR-0005."

### Rules

1. **The normalised domain is `[-1.0, 1.0]`.** Every value entering the protocol
   layer is in this range. Values outside it are clamped, never wrapped.
2. **The canonical on-wire representation is a signed integer scaled by
   `MOTION_SCALE = 1000`.** This is used on the network hop (`NetworkCommand`, bytes
   12..13 and 14..15, `int16` little-endian) and on the UART hop (`UartMotionPacket`,
   bytes 10..11 and 12..13, `int16` little-endian). The same scale and the same width
   are used on both hops.
3. **Both velocities use the same scale.** Linear and angular velocity share
   `MOTION_SCALE`. They are dimensionless fractions of their own respective maxima; a
   normalised angular velocity of `1.0` means "maximum turning rate", not "maximum
   linear speed".
4. **The conversion to the 8-bit domain happens only at the UART boundary**, in
   `normalise_for_uart` / `expand_from_uart`, using the factor `127 / 1000`. This is a
   boundary conversion between two encodings of the same normalised quantity, not a
   second canonical scale.
5. **The mapping is explicit and tested.** `normalise_for_uart(1000) == 127`,
   `normalise_for_uart(-1000) == -127`, `normalise_for_uart(0) == 0`, and
   `expand_from_uart(normalise_for_uart(x))` is within one unit of `x` for all `x` in
   range. The factor is `127`, not `128`, because `-128` is not representable in a
   symmetric signed byte with the same magnitude as `+127`.
6. **The physical unit is not defined yet, and must not be invented.** `1.0` means
   "the maximum commanded value", and the mapping from that to metres per second, PWM
   duty or wheel RPM is deferred until the driver, the motors and the encoders are
   confirmed and measured. **Not implemented — target design**: the physical
   calibration that would define "full scale", and the conversion from normalised to
   PWM that `firmware/arduino/src/kinematics.h` deliberately omits.
7. **The kinematics solver operates entirely in the normalised domain.**
   `left = clamp(linear - angular, -1, 1)` and `right = clamp(linear + angular, -1, 1)`.
   The multiplication by `255` shown in the original proposal's formula
   (`PWM_left = constrain((v - ω) * 255)`) is the *conversion to PWM*, which is a
   separate, not-yet-implemented step. The solver's output is a normalised wheel
   command, not a PWM value.
8. **Clamping is the failure mode of last resort everywhere.** `to_scaled`,
   `from_scaled`, `normalise_for_uart`, `expand_from_uart`, `ClampUnit` in the
   kinematics, and `SolveWheelSpeeds` in the arbiter all clamp rather than wrap. A
   value that is out of range is made safe, not reinterpreted.

### The physical conversion, when it exists

The normalised domain is deliberately a **fraction of the maximum**, not a fraction of
some absolute quantity, because the maximum is what the calibration determines. When
the drivetrain is confirmed, the calibration will supply:

```text
  max_linear_m_per_s   = <measured>
  max_angular_rad_per_s = <measured>
  PWM_left  = constrain(round((v - ω) * 255))
  PWM_right = constrain(round((v + ω) * 255))
```

with the wheelbase and the differential kinematic relationship determining how `v` and
`ω` map to the two wheels. The `255` factor is the Arduino's 8-bit PWM full scale. The
sign convention depends on the confirmed motor wiring and must be verified on the bench
before it is used to drive anything, as `firmware/arduino/src/kinematics.h` states.

## Consequences

### Positive

- There is one number to reason about. `MOTION_SCALE = 1000` means the same thing in
  Python, in the ESP32 firmware, and in the ADR set, and it is defined in exactly two
  files that must be changed together.
- The network hop and the UART hop now carry the **same** scale and the **same** width.
  A command's value does not depend on which hop it travelled.
- The draft's inconsistency is closed with an explicit, named, tested conversion rather
  than an implicit assumption at each end.
- Clamping makes out-of-range values safe. A planner bug that produces `5.0` produces
  full scale, not a wrapped sign-flipped command, and not an unbounded value that
  could overflow a downstream multiply.
- The normalised domain is decoupled from the unknown drivetrain. The team can build
  and test the entire protocol, planner and arbiter now, and attach the physical
  calibration later without touching the wire format.
- The kinematics solver contains no I/O and no physical constants, so it is unit
  testable without hardware.

### Negative / costs

- The wire carries `int16` where an `int8` would suffice on the UART hop. The motion
  packet is 18 bytes rather than the 14 it would be at `int8` on both velocities. On a
  115200 baud link this costs about 0.5 ms per frame, which is inside the budget but
  not free.
- The conversion to the 8-bit domain loses resolution on the UART hop: 1000 steps
  become 127, so a step of `1000/127 ≈ 7.9` normalised units. Below that, the UART hop
  quantises.
- The physical meaning of `1.0` is still undefined, so the vehicle cannot yet be
  given a speed limit in units a human would use. Until the calibration exists, the
  only meaningful statement is relative: "full scale is whatever the calibration
  says".
- `normalise_for_uart` and `expand_from_uart` are lossy in one direction and lossy in
  the other. A round trip through the 8-bit domain is not an identity, so the UART hop
  is not a transparent pipe. Anything that compares a commanded value against an
  applied value must account for that.
- `MOTION_SCALE` appears in two files plus the ADR. Changing it requires updating
  both, and any historical telemetry recorded under the old scale.
- The `255` PWM factor is assumed but unverified against the confirmed driver. The
  Arduino's `analogWrite` takes 0..255, so the factor is right for `analogWrite`; it
  is wrong for any driver that takes a signed or a different-range value, and that
  driver is not yet chosen.

### Risks accepted

- **"Full scale" is undefined until the drivetrain is confirmed.** Until then, a
  command of `1.0` means "as fast as this vehicle can go", which is the correct
  meaning but is not a speed limit. The speed limit for the campus course will have to
  be expressed in the normalised domain once the calibration exists, or as a separate
  clamp in Tier 1.
- **The draft's `PWM_left = constrain((v - ω) * 255)` formula has been partially
  superseded.** The `* 255` is the PWM conversion, which is deliberately not
  implemented. The solver's actual output is a normalised wheel command. The two must
  not be confused, and the ADR set records the distinction explicitly so that a later
  reader does not implement the `* 255` in the solver.
- The `±100` versus `±1000` distinction still appears in prose in
  `docs/ARCHITECTURE-v2.md` §6.2, which describes the UART packet as
  `[v:int8][w:int8]` while the implemented `UartMotionPacket` uses `int16` for both.
  The code is authoritative; the prose is a leftover from the draft and should be
  corrected.
- The 8-bit UART domain remains available for a future bandwidth optimisation, but
  using it would reintroduce a second width on the wire. If it is used, it must go
  through `normalise_for_uart` and `expand_from_uart` and nowhere else.

## Alternatives considered

**Keep `int16 ±1000` on the network and `int8 ±100` on the UART, as the draft
specified.** Rejected. This is the inconsistency this ADR exists to remove. It gives
the two hops different resolution, leaves the physical unit undefined, and makes the
command's meaning depend on its route.

**Use a single `int8` scale everywhere (e.g. `int8 ±127`).** Rejected as the canonical
scale. It is adequate for the UART hop but leaves little headroom for the network hop
if a future field needs to share the frame, and it makes the arithmetic less readable.
It remains the *target* domain for the UART hop, reached by explicit conversion rather
than by being canonical.

**Define the canonical domain in physical units (m/s, rad/s) from the start.** Rejected
for now. The drivetrain is unconfirmed, so any absolute limit would be a guess, and
`AGENTS.md` forbids guessed thresholds. The normalised domain is the honest choice: it
is exactly as informative as the physical one, and it does not require a calibration
that does not exist. It can be given physical meaning later without changing the wire
format, because `1.0` already means "full scale".

**Define the canonical domain in PWM units (0..255).** Rejected. It couples the
protocol to the Arduino's `analogWrite` range and to a driver that is not chosen, and
it loses the distinction between a command and the actuation that implements it. The
Tiers 1 and 2 should not know what PWM is.

**Use SI units with explicit physical limits (e.g. `v` in mm/s, `int32`).** Rejected
for the same reason as physical units, plus it would need a much wider field and would
make the frame size depend on a limit nobody has measured.

**Wrap instead of clamp on out-of-range values.** Rejected outright. Wrapping turns a
small planner overshoot into a sign flip, which is a full-speed reversal rather than a
bounded error.

**Use floating point on the wire.** Rejected. It costs four bytes per value instead of
two, introduces a NaN and infinity attack surface on the safety-critical hop, and makes
the cross-language byte-for-byte mirror harder to guarantee.

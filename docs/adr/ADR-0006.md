# ADR-0006: Latency budget as a measured budget; thresholds re-derived from bench measurement

- **Status:** Accepted
- **Date:** 2026-10-28
- **Deciders:** Autonomous Taxi team
- **Supersedes:** None

> **Implementation status:** this ADR records an architectural **decision**, not shipped code.
> The tiers, modules and firmware files it names are **specifications that have not been
> implemented** in this repository. The v0.1 simulation, the ESP32-CAM starter and the Arduino
> bench parser are what exist today. See [docs/VALIDATION.md](../VALIDATION.md) for the verified
> state of the current tree.


## Context

The latency budget is the constraint that determines whether the three-tier
architecture of ADR-0001 can work at all. It also determines the size of the safety
margins in ADR-0004 and ADR-0001: the watchdog timeout, the command freshness limit and
the emergency obstacle thresholds are all derived from how fast the vehicle responds
and how far it travels while responding.

This ADR records two things: the budget as currently specified, and the rule that
governs every number in it.

### The budget as specified

`docs/ARCHITECTURE-v2.md` §7 gives the design budget:

| Stage | Budget |
|---|---|
| Camera capture → JPEG available | 20–30 ms |
| JPEG encode + frame header | 5–10 ms |
| Network uplink (campus Wi-Fi) | 15–25 ms |
| Inference + occupancy update | 8–15 ms |
| VFH + controller | 2–5 ms |
| Network downlink | 15–25 ms |
| UART relay | 2–4 ms |
| **End-to-end** | **54–84 ms** (design target ≤ 120 ms) |
| Watchdog halt | 300 ms |

The end-to-end figure is the sum of the lower bounds (54 ms) and the sum of the upper
bounds (84 ms). The 120 ms is a design target ceiling. The 300 ms watchdog halt is the
fallback if the command stream stops entirely.

### The numbers these budgets interact with

> defined when the corresponding module is written. They are recorded here so that the budget and
> the constants are designed together rather than discovered to conflict later.

| Value | To be defined at | Meaning |
|---|---|---|
| `300` ms | `firmware/arduino/src/watchdog.h` — `kWatchdogTimeoutMs` | Command watchdog timeout |
| `0.3` s | `taxi/protocol/motion.py` — `DEFAULT_MAX_AGE_S` | Maximum accepted command age |
| `20` ms | `firmware/arduino/src/main.cpp` — `kLoopPeriodMs` | Tier 3 control loop period (50 Hz) |
| `25` ms | `firmware/arduino/src/sonar_fsm.h` — `kSonarPhaseIntervalMs` | Sonar round-robin phase interval |
| `5` ms | `firmware/arduino/src/sonar_fsm.h` — `kSonarEchoTimeoutMs` | Sonar echo timeout |
| `20` cm / `15` cm | `firmware/arduino/src/arbiter.h` — `kEmergencyCenterCm` / `kEmergencySideCm` | Emergency reflex thresholds |
| `100` / `50` / `33` ms | `firmware/esp32_s3/src/main.cpp` — `kTelemetryPeriodMs` / `kNetworkPeriodMs` / `kCameraPeriodMs` | Gateway task periods |

Every one of these is a **placeholder**. The implementation is to say so:

- `firmware/arduino/src/watchdog.h` (to be written): "The timeout below is a placeholder. It must be
  re-derived from the measured worst-case latency of the real path before it is used on
  hardware, per ADR-0006."
- `firmware/arduino/src/arbiter.h` (to be written): "Safety thresholds. These are placeholders for
  values that must be derived from measured stopping behaviour on the real bench, per
  ADR-0006. They are not physical limits and must not be used as such."
- `taxi/mission/safety.py` (to be written): "Placeholder safety thresholds. These mirror the firmware
  placeholders and must be re-derived from measured stopping behaviour before any
  physical use, per ADR-0006."
- `docs/ARCHITECTURE-v2.md` §7: "**Every physical threshold in this table is
  provisional.** The budgets were allocated by design reasoning, not measurement."

### The rule that simulator constants must not become physical thresholds

The project has an explicit and repeatedly stated prohibition. From `AGENTS.md`:

- "Never enable physical outputs with guessed pins, driver types or safety
  thresholds."
- "Firmware target builds and hardware tests are separate: report exactly which were
  run."

From `docs/ROADMAP.md`:

> "Choose all physical thresholds from these measurements, never from simulator
  constants."

From `docs/PROTOCOL.md`:

> "Choose physical thresholds from measurements, not the simulator constants."

The hazard this guards against is specific and easy to underestimate. The simulator
contains plausible-looking constants: `EMERGENCY_CENTER_CM = 20`, `EMERGENCY_SIDE_CM =
15`, a `DEFAULT_MAX_AGE_S = 0.3`, a simulated update expiry of 0.5 seconds. These
numbers are *demonstration values*. They are what makes the simulated dashboard
behave sensibly. If they are copied into the firmware, they acquire an authority they
never earned: the Arduino would refuse to move because a simulated number said a
20 cm obstacle was close, when the real vehicle at full speed needs more than 20 cm to
stop. The failure mode is asymmetric — a threshold that is too conservative stops the
vehicle, a threshold that is too permissive does not.

### The distinction between a build and a test

`AGENTS.md` and `docs/VALIDATION.md` both require this separation, and it applies
directly to every claim in this ADR.

`docs/VALIDATION.md` records the current state:

> "Firmware compilation: PlatformIO commands were attempted, but platform/toolchain
> downloads did not finish in this environment. Neither firmware target is claimed to
> compile successfully yet."

> "Actual camera, UART, sensors, driver, physical stopping or autonomous movement: no
> hardware connected."

> "Perception accuracy, localization accuracy, physical timing or stopping distance:
> not measured."

So: **no firmware target has been compiled in the development environment, and no
physical timing has been measured.** The budget in this ADR is a design allocation, not
a measurement.

## Decision

**The latency budget is a design allocation and a measurement plan, not a set of
validated limits.** It may be used to size the system and to decide what to measure.
It may **not** be used as a physical threshold, and no number in it may become a safety
threshold until it has been re-derived from bench measurement on the actual hardware.

### Rules

1. **Every stage budget in the table above is provisional.** It was allocated by design
   reasoning — by estimating what each stage plausibly costs — and not by measurement.
   It is a hypothesis about where the time goes.
2. **Every physical threshold is provisional**, including and not limited to: the
   `300 ms` watchdog timeout (`kWatchdogTimeoutMs`), the `0.3 s` command age limit
   (`DEFAULT_MAX_AGE_S`), the `20 cm` / `15 cm` emergency reflex thresholds
   (`kEmergencyCenterCm` / `kEmergencySideCm`), the `25 ms` sonar phase interval, the
   `5 ms` echo timeout, the `20 ms` Tier 3 loop period, and the `100 ms` / `50 ms` /
   `33 ms` gateway task periods.
3. **Simulator constants must never become physical thresholds.** The values in
   `taxi/mission/safety.py` (`EMERGENCY_CENTER_CM = 20`, `EMERGENCY_SIDE_CM = 15`),
   in the simulator, and in the dashboard are demonstration values. They may inform a
   starting guess for a bench experiment, and they may not be written into firmware as
   limits.
4. **Each threshold must be re-derived from measurement, and the measurement must be
   recorded** with its conditions: hardware revision, driver, motor, supply voltage,
   surface, load, and the number of trials.
5. **The thresholds must be derived from the vehicle's measured behaviour, not from the
   budget's arithmetic.** Specifically:
   - The **watchdog timeout** must exceed the measured worst-case end-to-end latency
     with margin, and must be short enough that the coast distance after a link loss
     is acceptable. Both constraints must be checked; the second usually binds first.
   - The **command age limit** must exceed the measured worst-case command age with
     margin, and must not exceed the watchdog timeout.
   - The **emergency thresholds** must exceed the measured stopping distance at the
     maximum permitted speed, converted from metres to centimetres, with margin.
   - The **Tier 3 loop period** must be short enough that the worst-case reaction to a
     detected obstacle is acceptable, given the sonar round-robin period.
6. **The budget must be re-derived as a whole, not patched.** If the measurement shows
   that inference exceeds its 8–15 ms allocation, the team must decide where to take
   the time from — a smaller input resolution, a faster model, a lower frame rate, or
   a larger end-to-end budget — rather than silently raising the watchdog timeout to
   absorb it.
7. **A claim of "the latency budget is met" requires a measurement on the real path.**
   Simulation timing, unit-test timing and the Python simulator's tick rate are not
   measurements of the physical system.
8. **Firmware target builds and hardware tests are separate claims.** A successful
   PlatformIO compile is a build result. It is not a hardware test, and it does not
   validate any threshold. A report must state exactly which of the two were run.
9. **The measured budget must be recorded in `docs/HARDWARE.md`** or a successor
   document, and the ADR set updated to reference the measurement, replacing the
   provisional values.

### The measurement plan

To discharge rule 5, the following must be measured on the real stack. This is the
plan; none of it has been performed.

| Quantity | How it is measured | Feeds |
|---|---|---|
| Camera capture → JPEG available | Timestamp in the ESP32 firmware at frame-buffer acquisition and at JPEG completion | Capture budget |
| JPEG encode + header | Same timestamps, subtracted | Encode budget |
| Network uplink | Timestamp at send on the ESP32, timestamp at receipt on the laptop | Uplink budget |
| Inference + occupancy update | Host-side timing around the detector call and the grid update | Inference budget |
| VFH + controller | Host-side timing around the planner and the controller | Planning budget |
| Network downlink | Timestamp at send on the laptop, timestamp at receipt on the ESP32 | Downlink budget |
| UART relay | Timestamp at UART write and at UART read, or an instrumented loopback | Relay budget |
| End-to-end | A single timestamp embedded in the command and read back on the Arduino | The `120 ms` ceiling |
| Worst-case, not typical | Deliberate induced load: busy Wi-Fi, a slow frame, GC pause, an inference backlog | The watchdog timeout |
| Stopping distance | Vehicle at maximum permitted speed; trigger a stop; measure distance | The emergency thresholds |
| Link-loss coast | Vehicle at maximum permitted speed; kill the Wi-Fi; measure distance until stop | The watchdog timeout |

The "worst-case, not typical" row is the one that matters. A budget derived from mean
latency is a budget that will be exceeded. The watchdog must be sized against the
worst case observed under induced load, because the worst case is exactly when the
vehicle is most likely to be doing something that needs to stop.

### What the numbers must satisfy

The derived thresholds must satisfy these relationships, each of which is currently
unverified:

```text
  measured worst-case end-to-end latency  <  command age limit  <=  watchdog timeout

  stopping distance at maximum permitted speed  <  emergency threshold
     (converted to centimetres, with margin)

  sonar round-robin period (3 x 25 ms = 75 ms)  <  Tier 3 loop period budget for
     obstacle detection, given the maximum permitted speed
```

The first line is a contradiction waiting to happen if it is not checked. If the
measured worst-case latency exceeds the command age limit, every command will be
rejected on arrival and the vehicle will not move — a fail-safe failure that would be
immediately visible on the bench but would invalidate the whole configuration. If the
command age limit is set above the watchdog timeout, the freshness check becomes the
weaker of the two and the age check is doing no work.

## Consequences

### Positive

- The budget remains useful for its actual purpose: sizing the system, sequencing the
  build, and deciding what to measure first. Nothing is lost by labelling it
  provisional.
- The prohibition on simulator constants becoming physical thresholds is explicit and
  traceable to a single ADR, so a reviewer can check it.
- The relationship constraints between the thresholds are stated, which turns the
  configuration from a set of independent numbers into a checkable system.
- The "worst-case, not typical" requirement stops the most likely error: sizing the
  watchdog against a mean latency.
- Separating a build result from a hardware test keeps the project's evidence honest,
  which `docs/ROADMAP.md` requires: "Firmware claims need compiler and bench logs;
  driving claims need physical measurements."
- The measurement plan is written down before the hardware is available, so the bench
  session is not spent improvising what to measure.

### Negative / costs

- The 300 ms watchdog timeout is currently the only backstop, and it is a guess. Until
  it is measured, the vehicle's behaviour under a link loss is unknown.
- The emergency thresholds may be wrong in the unsafe direction. `20 cm` for the
  centre sensor was chosen without any knowledge of the vehicle's stopping distance.
- Every threshold change touches firmware, the host mirror and the tests. The
  host-side mirror in `taxi/mission/safety.py` is to exist precisely so the simulator can
  exercise the same rules, which means a threshold change must be made in both places.
- The measurement work is a real cost: it needs the confirmed boards, a confirmed
  driver, a measured course and a stopwatch or an instrumented logger.
- Until the measurements are done, the honest answer to "what is the vehicle's
  stopping distance?" is "unknown", and any performance claim in the README, the
  dashboard or a milestone report must say so.

### Risks accepted

- **The provisional values are in the shipped code.** `kWatchdogTimeoutMs = 300` and
  the emergency thresholds are constants in the firmware, and `DEFAULT_MAX_AGE_S = 0.3`
  is in the host protocol module. They are used by the simulator and by the firmware
  self-test, and they are guarded by comments and by this ADR rather than by a
  mechanism that prevents their use on hardware. The mitigating control is structural
  rather than declarative: the firmware has **no actuator GPIO** and no way to enable
  the motors, so a wrong threshold cannot currently cause motion. `firmware/arduino/src/main.cpp`
  says so: "The result is that the vehicle cannot move and every sensor reading stays
  invalid, while the arbitration order and timing can be verified on the bench before
  any driver is wired."
- **`docs/ARCHITECTURE-v2.md` §6.2 contains a stale description** of the UART packet
  as `[v:int8][w:int8]` while the implemented `UartMotionPacket` uses `int16` for both
  velocities. The code is authoritative. The prose should be corrected so that a
  reader does not derive a physical range from an obsolete field width.
- The bench measurement of the stopping distance will need to be redone if the
  drivetrain changes — a different motor, a different driver, a different battery, a
  different surface, a loaded or unloaded vehicle. A measured threshold is a property
  of a configuration, not of the project.
- A measurement taken on the bench under good Wi-Fi conditions may not survive a
  campus-wide network with many clients. The "induced load" row of the measurement
  plan exists to expose this, but the bench conditions must be recorded alongside the
  result.
- If the measurement shows the budget cannot be met on the chosen hardware, the
  response must be a change to the system (a faster model, a lower resolution, a
  different frame rate), not a relaxation of the safety thresholds. The thresholds
  follow the physics; the budget follows the implementation.

## Alternatives considered

**Treat the budget as a validated set of limits and design against it.** Rejected. The
budget was allocated by reasoning, not measured, and `docs/VALIDATION.md` records that
no physical timing has been measured. Designing against unvalidated limits as though
they were facts is the failure this ADR exists to prevent.

**Measure only the end-to-end latency and keep the per-stage splits as design values.**
Rejected as insufficient. The per-stage splits are what tell the team *where* to
optimise when the end-to-end figure is over budget, and they are what determine the
size of the sonar and watchdog margins.

**Set the watchdog timeout generously (say 1 s) so that measured latency never
exceeds it.** Rejected. This trades a latency failure for a safety failure: a longer
watchdog means a longer coast after a link loss, and the coast distance is a physical
safety quantity. The watchdog is bounded by the stopping distance, not by the latency.

**Derive the thresholds from the simulator, since the simulator already implements the
arbiter.** Rejected. The simulator's obstacle distances are fabricated. Deriving a
physical stopping threshold from them would be inventing the number and then citing
the simulation as its source.

**Remove the placeholder thresholds until they are measured.** Rejected. The
placeholders are needed for the bench-only firmware to be structurally complete and
testable, and for the host-side mirror to have something to mirror. They are labelled
as placeholders in code, in tests and in this ADR set.

**Use a statistical margin (e.g. three standard deviations) instead of a fixed
engineering margin.** Deferred. It is a reasonable way to express a margin once the
latency distribution is known, and it becomes available after the measurement. It is
not available now, and a distribution cannot be assumed before it is collected.

**Re-derive the thresholds on the simulator's timing to get an early signal.** Rejected
for the same reason as above: the simulator's timing is not the physical system's
timing.
